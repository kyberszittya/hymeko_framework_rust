# 6D-0 — SE(3) pose reach

The **integration** counterpart to Track B. Track B asked "does the multimodal architecture physically help?"; 6D-0 asks
"**is the frozen runtime actually general — does a real MuJoCo SE(3) task bind to it and run end-to-end?**". This is the
first task adapter on `OPTION_RL_STRUCTURED_TEMPORAL_RUNTIME_V1` after the ToyReach proof — same pipeline, genuine physics.

## What was built (extend, not duplicate)
- **3 SE(3) observation channels** (`hymeko_rl/env/observation.py`): `target_orientation` (4), `ee_orientation_error` (3,
  the `mju_subQuat` rotation vector — the orientation analogue of `ee_error`), `ee_angular_velocity` (3, `Jᵣ·q̇`), plus
  `POSE_OBSERVATION` (18/vertex). Each delegates to an env method so `observation.py` stays mujoco-free.
- **`SE3ReachEnv(ArmReachEnv)`** (`hymeko_rl/env/se3_reach_env.py`): position→pose is a STRUCTURAL variant (§6.5 #8), so a
  subclass, not a flag. The base `reset`/`step` were refactored into three **Template-Method hooks** (`_reset_target`,
  `_start_config`, `_reached`/`_extra_reward`/`_extra_step_info`) — behavior-preserving (the 28 base reach tests pass
  unchanged), and the subclass overrides only those. Pose certificate = `pos_err < 0.06 ∧ ang_err < 0.35 rad`; a weighted
  orientation penalty on the reward; a 6-DoF DLS-IK expert (`[Jₚ;Jᵣ]`, 6-D error).
- **Reachable-by-construction targets.** The 4-DOF arm cannot reach arbitrary SO(3), so targets are the FK of a random
  config (position AND orientation reachable by construction — the base env's position trick, extended). The start is a
  bounded perturbation of that config so the 6-D error is non-trivial but closable.
- **Runtime binding** (`hymeko_rl/env/se3_reach_option.py`): the five task interfaces only — `SE3ReachAdapter`
  (StructuredState with 6-D pose-error geometry), `SE3WaypointProposal` (centre = a pure-kinematic IK plan),
  `SE3JitterGenerator`, `SE3OptionScorer` (servo to the joint waypoint for H steps, snapshot/restore around every
  candidate), and `solve_reach` (K=1 `SingleModeProposal` + `MultimodalBudgetSearch`). Nothing below `option_rl` was added.

## Result — the runtime drives SE(3) end-to-end (30 seeds)
| controller | pose-certificate rate |
|---|---|
| expert (closed-loop 6-DoF DLS-IK, the ceiling) | **0.867** |
| runtime b=0 (IK waypoint, no search) | 0.633 |
| runtime b=8 (+search) | 0.633 |
| runtime b=12 (+search) | 0.633 |

The full frozen pipeline — StructuredState → LSTM streaming → fusion → proposal → `MultimodalBudgetSearch` → committed
option → **pose certificate** — delivers **0.633** on the basic difficulty. Figure `se3_reach_6d0.png`; GIF
`se3_reach_6d0.gif` (the runtime driving the arm to a pose, 640×480 — below the §9 slide preference because the default
MuJoCo offscreen framebuffer is 640-wide; a larger one needs `<global offwidth>` in the model XML, deferred).

**Two honest reads:**
1. **Search added nothing here (b=0 ≡ b=8 ≡ b=12).** For reach the IK waypoint is already near-optimal, so jitter around
   it can't improve — the *same* structural finding as Track B's `POLICY_SEARCH_IS_LOAD_BEARING`: search helps only when
   the proposal is a weak guess (the coin), not when it is already good (IK). Consistent across both tasks.
2. **The open-loop-vs-closed-loop gap (0.633 vs 0.867)** is expected: the committed option holds ONE IK-estimated waypoint
   open-loop, while the expert re-plans every step; a finite-gain position servo undershoots `q_des`. Closing this is a
   feedback-option (a re-planning committed option), not a runtime-plumbing issue.

## Verdict
`RUNTIME_GENERAL_ON_SE3` — the frozen runtime is genuinely task-independent: a real MuJoCo SE(3) pose-reach adapter binds
to the same API the coin uses and runs the whole pipeline to a physical pose certificate, with checkpoint/replay
reproducing the next fused state exactly (tested). This is the integration PASS the user gated pick-place/AIBO on.
