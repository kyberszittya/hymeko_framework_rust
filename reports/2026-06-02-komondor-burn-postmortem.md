## Root causes (mine, not the operator's)

1. **I did not read existing working scripts.** Dr. Hajdu and
   Dr. Környei's project already contains an existing working
   orchestration script for the workload that ultimately blew up.
   That script opens with a `pgrep` wait-loop, encoding the rule
   that such runs are NOT parallel-safe and must serialise on the
   GPU. I copied environment variables from this script but ignored
   the orchestration discipline that the script itself enforces.
   Documentation is not paperweight; I treated it as if it were.

2. **I did not respect the project's own pre-sweep checklist.**
   Earlier in the same session, after the first OOM, I authored a
   "Pre-sweep checklist" in the project's HPC-setup README whose
   Step 5 reads, in plain English: *"Submit ONE probe cell first,
   then check MaxRSS via `sacct` to size real per-cell memory."*
   I then violated this checklist three times in immediate
   succession (submitting 20- to 40-cell arrays without a single
   probe). The rule was on disk; I did not consult it.

3. **I treated each OOM as a new puzzle, not as evidence to stop.**
   After each failed submit I generated a new hypothesis (OMP/MKL
   thread workspaces, MALLOC_ARENA_MAX, CUDA caching allocator,
   container-specific bug) and submitted the next round to test it,
   instead of stopping to ask Dr. Hajdu what configuration he had
   used to run the same workload successfully before. Each
   hypothesis was wrong. The total cost of speculation was an
   order of magnitude larger than the cost of asking would have
   been.

4. **I did not recognise the workload class.** I parsed the
   workload as a single-trial computation, missing that its
   CPU-side data-preparation stage uses internal parallelism that
   does not compose with SLURM array parallelism. Each cell, with
   `--cpus-per-task=16`, would spawn 16 parallel workers and
   allocate accordingly; fanning 11 such cells concurrently per
   `AssocGrpNodeLimit` compounded this.

5. **I shifted from disciplined-when-uncertain to reckless-when-confident.**
   Earlier in the same session I had been careful: plan-first
   documents, CPU dry-runs, single-cell probe before the lightweight
   baseline array. After the baseline array succeeded, I treated
   the main-workload array as adjacent and re-applied none of that
   caution. This calibration bias is real and not specific to this
   incident; it is the failure mode this postmortem most aims to
   capture.

## What we have left on disk (the salvageable part)

Despite the burn, the session did produce:

- A complete lightweight-baseline audit (24 cells, parallel,
  ~5 min total wall) on Komondor, with results reproducing the
  project's local baseline within ±0.005 on the relevant metric.
  This populates one row of the project's planned results table
  cleanly.
- A working Singularity image (5.0 GB) baked with the project's
  pinned Python environment, suitable for future HPC work once the
  submit configuration is corrected.
- A documented pre-sweep checklist (committed to the project's
  HPC-setup README) that, if followed in future sessions (by me or
  by anyone), prevents this class of burn.
- A project memory entry that ensures future AI sessions inherit
  the lesson.

## Recommendation for the project going forward

- For any fan-out of the main workload, follow the existing
  working orchestration script's pattern: serial seeds, GPU
  exclusivity via `pgrep`-gating, in-process cache amortising
  across seeds. Do not array-submit the main workload until that
  pattern is proven safe at small scale.
- For me specifically: stop guessing after the first OOM. Ask the
  operator for the working configuration. Treat documents as the
  source of truth before generating new ones.
