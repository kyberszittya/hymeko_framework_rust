## 4. The four classifications

**NATIVE_DECLARATIVE** (the source of truth lives in `.hymeko`):
- Phase automaton — phases PUSH/BRAKE/RELEASE/HANDOFF + terminals, signed `on <event> to <phase>` transitions, guard-event
  names (§1).
- Certificate/monitor semantics — `@certificate` tolerances (center_tol/settle_vel/held_dwell/entry_tol) + the strict/
  handoff/containment/K6 predicate structure (§2A).
- Skill routing — per-phase `skill_role`/`training_state`/`binding`, the frozen skill's `handoff_certificate` +
  `checkpoint` identity + `checkpoint_sha` (§3).
- Option-RL run contract — option_spec (Bellman action = θ_center, selected = provenance), proposal_policy (checkpoint,
  trainable), candidate_generator/scorer, fixed_budget_search (budget 8), semi_mdp_target (γ^τ, terminal-no-bootstrap, γ),
  replay_contract, trainer (SAC primary / TD3 control), evaluation_contract (physical K6 paired, not critic-Q-alone),
  run_manifest (train/dev/final) (§4).

**GENERATED_RUNTIME_CONFIGURATION** (produced from the parse, not hand-written):
- The framework `SkillRoute` — generated from the §3 routing.
- The `RLConfig`/runtime config — generated by `to_runtime_config()` (b, γ from the graph).
- The `MonitorSpec` — read from `@certificate`; drives the online monitor.
- The automaton transition table driving `execute_one_option` (via `spec.step`).
- The per-step skill-binding trace — derived from the phase trace + routing.

**EXECUTABLE_BACKEND_BINDING** (bound by name; numerics stay in Python/backend, correctly so):
- Guard predicates (push_reached, brake_centered, …) evaluated on the live sim state.
- Phase laws → actions (push/brake/release amplitudes of θ; frozen pi_0 settling policy).
- `PythonTaskMonitorBackend.observe` (the STL-equivalent counting); `structured_random_around` (generator);
  `structured_score` (scorer); SAC/TD3 (`train_semi_mdp`); the replay buffer; the optimizer; the MuJoCo simulator.

**NOT_YET_NATIVE** (still Python, or deliberately deferred):
- The env's internal `_strict` counter — a fail-closed SHADOW (gated equal every step); deleting it is a `coin_rl_env`
  CORE change, deferred.
- The Rust `hymeko_monitor` online verification — §2B, deferred (needs PyO3; §6 proposes the interface).
- `OptionReward` weights (w_k6, w_handoff, …) — Python constants; declarable in `.hymeko` like the certificate tolerances
  (small follow-up).
- `RLConfig` hyperparameters beyond b/γ (lr, batch, warmup, …) — engine defaults, not in the description.

## 6. Remaining duplicated configuration

- `std_amp`/`std_dur` (0.6/2.0) are declared in the `.hymeko` `@generator` node **and** are defaults in `search_select` —
  the description declares them but `to_runtime_config` does not yet wire them into the search wrapper. Minor; a follow-up
  can thread them through so the `.hymeko` is the sole source.
- `OptionReward` weights and the non-b/γ `RLConfig` fields are Python-side (see NOT_YET_NATIVE). No *contradictory*
  duplication (the `.hymeko` values equal the code values, gated where they matter), but full single-sourcing of these is
  outstanding.

## 7. Exact claims and non-claims

**Claims (supported by gates):** the executed carry-option control **is** its HyMeKo description — phase automaton (§1),
delivery certificate as an online trace-monitor (§2A), trained/frozen skill routing (§3), and the option-RL run contract
(§4) all derive from `.hymeko`; the runtime config is regenerated from the parse without hand-written duplicate topology; a
query over the parsed graph answers the whole run; the load-bearing RL invariants (Bellman = θ_center, selected = provenance,
budget fixed, γ^τ, terminal-no-bootstrap, trainable upstream / frozen downstream, physical selection) are declared and
validated fail-closed; an existing Stage-5 checkpoint loads and reproduces the update-0 eval contract.

**Non-claims:** the Rust `hymeko_monitor` crate does **not** yet online-verify the run (that is §2B); the env's `_strict`
counter still exists internally (shadow, gated); reward weights and most optimizer hyperparameters remain Python backend
config; SAC/TD3/replay/optimizer numerics are **not** reimplemented in the DSL (by design — HyMeKo declares their role, not
their arithmetic). The Stage-5b RL result is unchanged: **CONSISTENT_POSITIVE_SAC_LEAN** (4/4 SAC seeds beat their own
update-0, median +0.042) with **RL_SUPERIORITY_NOT_YET_STATISTICALLY_ESTABLISHED** (per-seed CIs span 0).

## 8. Proposed narrow PyO3 interface for §2B (NOT implemented)

A `RustStlMonitorBackend` that satisfies the existing `MonitorBackend` Protocol — a backend swap, no executor change:

```rust
// hymeko_monitor PyO3 surface — maps 1:1 onto hymeko_rl.coin_delivery.coin_carry_monitor.MonitorBackend
#[pyclass] struct RustStlMonitor { /* wraps StlMonitor over the signed-incidence hypergraph state */ }
#[pymethods] impl RustStlMonitor {
    #[new] fn new() -> Self;
    fn reset(&mut self, center_tol: f64, settle_vel: f64, held_dwell: usize, entry_tol: f64,
             initial_dtz: f64, initial_touched: bool);
    fn observe(&mut self, dtz: f64, speed: f64, touched: bool, contact: bool, terminated: bool) -> PyObject; // {strict,exited,handoff_now}
    fn verdict(&self) -> PyObject;   // {k6, reached_handoff, contain_exit_ct, max_strict, terminal, events}
    fn snapshot(&self) -> PyObject;  // {strict, max_strict, contain_exit, handoff, delivered}
}
```
Python: `make_monitor("rust")` returns `RustStlMonitorBackend(RustStlMonitor())`; the `MonitorSpec` (from the same
`@certificate`) feeds the tolerances; the same STL predicates are evaluated in Rust. Rollout of the Python and Rust backends
in shadow gives full-trace parity on a replay bank; then the Rust backend becomes primary. This is a core/Rust change and is
**gated on explicit approval** (§2B), a separate, well-bounded milestone. The larger statistical campaign
(≥6 seeds / larger final panel, or the multi-object benchmark) is the other separate branch.
